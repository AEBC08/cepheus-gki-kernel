## 4. 构建形态

`build_kernel.sh`（已验证内容）：

- `DEFCONFIG=vendor/sm8150-qgki_defconfig`，`DEVICE=cepheus`，合并 `arch/arm64/configs/vendor/xiaomi/{sm8150-common.config,cepheus.config}`
- `make ARCH=arm64 LLVM=1 LLVM_IAS=1 Image.gz dtbs dtbo.img dtb.img`
- 产物：`out/boot/kernel`（= `Image.gz`）、`kernel_dtb`、`dtbo.img`
- **单体**：`sm8150-qgki_defconfig` 中仅 1 行 `=m`（`=y` 为主），含 `CONFIG_QCOM_KGSL=y`、`CONFIG_LTO_CLANG=y`、`CONFIG_MODVERSIONS=y`、`CONFIG_GKI_HACKS_TO_FIX=y`、`CONFIG_LOCALVERSION="-qgki"`
- 无 `modules.list`（仅 `modules.list.msm.lahaina`，LAHAINA 原始文件）→ **实际未走模块加载流程**

## 5. 对 5.10 项目的意义

**可直接复用的成果**

1. SM8150 平台 DTS/DTSI 与 cepheus 机型 DTS（含电池、面板、相机 sensor、smb1390、红外）——省下最耗时的"平台摸清"阶段。
2. 一组"把 4.14 驱动往 msm-5.x techpack 结构靠"的实践先例（audio-kernel from LA.UM.9.14 QSSI16、venus NV12 兼容、ion legacy 警告屏蔽、Xiaomi charging logger ABI 保留）。
3. 传统 boot.img 打包形态（`Image.gz` + `dtb.img` + `dtbo.img`），说明无 `vendor_boot` 可行。

**必须重做的部分**

1. 底板从 5.4 换到 5.10（ACK android12-5.10）→ techpack 全部跟 CAF msm-5.10 版本，DTS binding 需重写。
2. 5.4 里的 `ion` 兼容垫片在 5.10 需重新评估（5.10 仍保留 CAF ion 兼容，但需实测 blobs）。
3. 模块化缺失 → 5.10 阶段才做（D003）。

**判断（未验证）**：作者已验证 HyperOS 2 启动并跑通指纹/面容，说明 display（含 FOD 通路）+ touch + biometric HAL 链路在该树上是成立的；迁到类原生 ROM 的用户空间差异主要在 HAL/GMS 层，内核侧期望更宽松——这与用户"回退类原生相对简单"的判断一致。
